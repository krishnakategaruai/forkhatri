## Cross-flow conventions (apply to every UX item below)

**Platform: mobile-first WEB app (Product Manager standing reminder).** Vyapar is a responsive web app used primarily in phone browsers, not a native Android/iOS app. Every wireframe below is designed for a small touch viewport first; desktop is the responsive fallback (lists become two columns, sheets become centred dialogs, the bottom nav becomes a left rail at >= 900 px). Wherever a comparable native-app pattern is adapted, the web equivalent is what is specified: (1) install = PWA installability (browser "Add to Home screen" prompt, only offered after a successful action, never on the platform's sign-in/welcome screens, which are not Vyapar's); (2) OTP = the parent platform's shared OTP component (SMS code typed by the member, with `autocomplete="one-time-code"` / WebOTP autofill where the browser supports it — Chrome Android; Safari autofill — and no dependence on it), which Vyapar reuses only to verify a listing's contact number (FR07); sign-in itself is the platform's and is never a Vyapar screen; (3) location = browser Geolocation permission prompt with manual locality entry as the always-available path; (4) notifications = browser Notification permission (Web Push) requested contextually, with the in-app inbox as the always-available path; (5) share = Web Share API (`navigator.share`) where available, otherwise a "Copy link" / "Share on WhatsApp" fallback row; (6) camera/file = `<input type="file" accept="image/*,application/pdf">` (with `capture` hint on phones), never an assumed native picker; (7) "bottom sheet", "bottom navigation" and "push" are web components implemented with CSS transforms, and every gesture (swipe-down, pull-to-refresh) has a button equivalent because touch gestures on the mobile web are less reliable than in native apps; (8) back = browser history (`pushState`) so the hardware/browser Back button pops screens and closes sheets exactly like the header back arrow; (9) offline = Service Worker cache of Saved, Activity and recently viewed items (UX03).

**Authentication is the parent platform's (product owner standing correction, 2026-09-14).** "User login, authentication will be done by one source of truth that is parent: ForKhatri." Every ForKhatri module consumes the single shared sign-in provided by the parent ForKhatri app (Identity & Trust Service, ARCHITECTURE.md ADR-004: "no module ever forks its own login/identity table"). Vyapar therefore designs no Launch, Welcome, Sign-in, Sign-up, OTP-login, Forgot-password or Log-out screen. Vyapar's UX starts at the platform's return point — the member is already signed in when Vyapar opens (UX01 entry) — and ends at a "Back to ForKhatri" exit (UX13) that hands control to the parent app; logging out is a platform action performed there. If Vyapar ever finds no valid session (expired, revoked, or the FR50 15-minute read-only window elapsed), it hands back to the platform sign-in and never renders a login of its own. The only OTP in Vyapar is business verification of a listing's contact number (FR07, UX04/UX05/UX14/UX22), which reuses the platform's shared OTP component and is not a sign-in.

**Comparable applications (corrected 2026-09-13 after the Product Manager asked whether the right apps were being referenced).** Vyapar's true peer set is Indian *community* apps that combine a member business directory with jobs/opportunities inside a caste or samaj network — not general marketplaces. **Navigation shell (UX03).** Five bottom destinations, always-visible labels: Discover (opportunities) · Businesses (businesses & professionals directory) · Post · Activity · Profile. Notifications are an app-bar bell, not a tab (Vyapar_02 §1). Discover and Businesses are peer tabs of equal weight — the Product Manager's decision that Vyapar works like an ordinary business-discovery app as well as an opportunity network (UX03 DEC-004). Tapping the active tab scrolls its list to top; tapping it again while at top does nothing.

**Transition vocabulary.** (a) *Tab switch*: instant content swap with a 150 ms crossfade, no slide — top-level destinations are peers, not a stack (Android navigation principles: fixed start destination + back stack, opened). (b) *Push*: list → detail slides in from the right; system Back and the header back arrow both pop. (c) *Modal bottom sheet*: slides up over a scrim with a drag handle; dismissed by scrim tap, swipe-down, header Close, or Escape/Back; used for short decisions (reasons, filters, explanations, confirmations). (d) *Full-screen compose modal*: slides up from the bottom, closed by an X at top-left with an "Discard changes?" confirm when dirty; used for multi-field creation (Composer, listing setup, enquiry, report). (e) *Loading*: skeleton placeholders for full-screen lists and detail pages; an inline spinner inside the pressed button for single actions; a determinate progress bar for uploads (NN/g skeleton-screens guidance, opened). (f) *Success*: a 400 ms check-mark micro-animation inside the primary button, then route; no full-screen celebration. (g) *Pull-to-refresh* on Discover lists, results and Activity only; never on detail or forms. (h) *Reduced motion*: when `prefers-reduced-motion` is set, all slides become 100 ms fades and the check-mark becomes static.

**Touch & accessibility baseline (FR43, WCAG 2.2 AA).** Every tap target is at least 48×48 CSS px with 8 px spacing (exceeds SC 2.5.8's 24×24 minimum, opened). No information by colour alone: every state label is text (plus an icon where helpful). No drag-only path: anything achievable by swipe (dismiss sheet, refresh) also has a button. Visible focus ring on all controls; focus moves to the sheet title when a sheet opens and returns to the invoking control on close; page title announced on every route change; error messages name the field and the fix and are linked via `aria-describedby`. Text resizes to 200% without loss (no fixed-height rows). Infinite-scroll lists also expose a "Load more" button.

**Hindi / Telugu text expansion (FR42).** Devanagari and Telugu need taller line boxes and more width than English. Rules for every wireframe: (1) bottom-nav labels are single words, ≤ 10 characters in each language; (2) segment/chip labels reserve 35% extra width over the English string and wrap to two lines rather than truncating; (3) body line-height ≥ 1.6, minimum body size 16 px, no all-caps styling; (4) buttons are full-width on phones so long Hindi/Telugu labels never overflow; (5) no text baked into images; (6) member-authored content keeps its own language with a small language tag ("हिन्दी") and is never machine-translated on trust/safety/price fields; (7) fonts: a Noto Sans family (Latin + Devanagari + Telugu) so all three scripts share one type system. (Sources: Translated.com text-expansion article and Noto docs — search snippets only; the rules above are the design decision, not a claim about those pages.)

**Instrumentation (FR45).** Each flow emits the listed events with level tags: UX06/UX08 impression, search (zero-result flag); UX07/UX09 view, save, share, hide-with-reason; UX12 enquiry submitted / state change; UX16 review submitted; UX15 report submitted; UX18 notification sent/opened/muted; UX02 setup step completed/abandoned; UX20/UX21 promotion purchased/active/completed; UX12 outcome confirmed. - Stale/Expired queue: columns title · owner · last confirmed · state · checkbox; toolbar "Remind (n)" / "Expire (n)" → confirm dialog "Expire 12 opportunities? Owners will be notified." (FR48 bulk confirmation with counts).
- Taxonomy: search field · tree/list of concepts with aliases · panel "Unmapped labels (23)" (from FR04/FR01 free text) each with Buttons "Map to…" (search) · "Add as new concept" · concept actions "Rename" · "Merge into…" (aliases preserved) · version history row "v41 · applied to search 14:05" (5-minute refresh, FR48). Member-entered text is never edited (read-only display of examples).
- Commercial: Products — list of products with versions; version row shows price, tax, duration, "Orders: 128 (locked)"; Button "Create new version" (form). Promotions & Entitlements — filter by state; row → detail (order, price version, payment reference, history). Refunds/credits — queue: order, requested amount, reason; Buttons "Approve" (amount field capped at order value; over-value rejected inline) · "Reject" (reason). Dead-letter list (FR52) — failed adjacent calls with Retry. Diagnostics — input record id / member id → "Eligibility: excluded — location outside radius (on-site)" or "Eligible — score 0.72: capability 0.30 · location 0.15 · freshness 0.12 …" (read-only; no override control exists). Audit search — filters actor · object id · action · date range → table → "Export CSV".
- Metrics: period select (7/30/90 days) · cards: Relevant Opportunity Connections · Opportunity Coverage · Relevant Discovery Rate · Opportunity Action Rate · Successful Connection Rate · Discovery-to-enquiry rate (listings) · Time to first relevant opportunity · Freshness · Zero-result rate · Reports per 1,000 interactions · Notification opt-out rate · Promotion repeat rate · Revenue / refunds — each labelled with its outcome level (impression / view / action / attributed / confirmed) and "n < 10 suppressed" where applicable. No profile-completion metric anywhere (FR46).
- Hindi/Telugu notes: operator UI English-first; member notifications generated in the member's language.
