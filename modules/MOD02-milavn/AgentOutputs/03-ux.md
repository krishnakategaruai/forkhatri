## UX01 — Authentication
> **Ownership correction (2026-09-13, product decision):** user login and authentication have one source of truth, the parent **ForKhatri platform** (Common Platform Identity & Trust Service). Milavn does not design, build, or test its own Splash, Sign Up, Log In, Forgot/Reset Password, OTP, or Logout/Delete-Account flows; it consumes the member identity the platform has already resolved (`identity_bridge` in `architecture.md`). The text below is kept unchanged for traceability and as the hand-off brief to the platform team; nothing in it is Milavn implementation scope.

**Traces from:** FR076, FR077, FR078, FR079, FR080 (all newly added by this step to BR01)
**Traced to:** UI01 (Step 4 UI)
**Priority:** P0
**Status:** Draft
**Confidence:** High

**Flow**
Splash (auto-routes) → [new user] Sign Up → OTP Verification → First-Run
Onboarding (UX02) → Home; or [returning user] Log In → Home; Log In also
exits to Forgot Password → OTP Verification → Set New Password → Log In.

**Screen-by-screen detail**
| Screen/state | Value delivered | Contains | Primary/secondary actions | Touch/interaction model | Sentiment/tone |
|---|---|---|---|---|---|
| Splash | Fast, reassuring entry while auth state resolves | Brand mark, background tone | (auto-advances) | None — timed, ≤1.5s | Calm, confident, unhurried |
| Sign Up | Fastest path to a real account | Email/phone input, single "Continue" action, link to Log In | Continue (primary); "Already have an account? Log in" (secondary) | Tap to focus input; auto-detects email vs. phone format | Welcoming, low-effort |
| OTP Verification | Confirms identity with minimal friction | 6-box code input, countdown-gated resend link, edit-number link | Verify (auto-submits when 6 digits present); Resend (after countdown); Edit number | Autofill from SMS/email where platform supports it (verified pattern, see Research) | Efficient, not anxious |
| Log In | Fast return path | Email/phone + password inputs, "Forgot password?" link, "Sign up" link | Log In (primary); Forgot password / Sign up (secondary) | Standard form tap-to-focus | Frictionless, familiar |
| Forgot Password | Recovery without dead-ending the user | Email/phone input, neutral confirmation message | Send reset link/code | Same as Sign Up | Reassuring, neutral (never confirms/denies account existence) |
| Set New Password | Completes recovery | New password + confirm fields, strength hint | Set Password (primary) | Standard form | Relief-oriented, brief |

**Wireframes**
- Splash
  - Content: centered brand mark, subtle background tone
  - (no interactive elements — auto-advances on auth-state resolution)
- Sign Up
  - Header: "Join Milavn" title, back-to-splash disabled (entry point)
  - Content:
    - Input: email or phone (single field, auto-detected)
    - Button: "Continue" -> OTP Verification
    - Text link: "Already have an account? Log in" -> Log In
- OTP Verification
  - Header: "Verify it's you", subtext naming where the code was sent
  - Content:
    - 6-box code input (auto-submits at 6 digits, supports platform autofill)
    - Text link: "Resend code" -> re-triggers send (disabled during countdown)
    - Text link: "Edit number/email" -> back to Sign Up
- Log In
  - Header: "Welcome back"
  - Content:
    - Input: email or phone
    - Input: password (with show/hide toggle)
    - Button: "Log In" -> Home (UX04) or Onboarding (UX02) if first login post-verification
    - Text link: "Forgot password?" -> Forgot Password
    - Text link: "New here? Sign up" -> Sign Up
- Forgot Password
  - Header: "Reset your password"
  - Content:
    - Input: email or phone
    - Button: "Send reset code" -> OTP Verification (reused)
- Set New Password
  - Header: "Choose a new password"
  - Content:
    - Input: new password
    - Input: confirm password
    - Button: "Set Password" -> Log In

**States**
| State | Trigger | What the user sees |
|---|---|---|
| Loading | Submitting any form on this flow | Button shows an inline spinner, label replaced (per Research: spinners for short blocking actions, not skeletons) |
| Empty | N/A (forms, not lists) | — |
| Error | Duplicate account (Sign Up), wrong credentials (Log In), invalid/expired code (OTP) | Inline, field-adjacent error text — never a full-screen error (per UX18's cross-cutting rule) |
| Success | Verification/login completes | Immediate route to the next screen; no interstitial "success" screen (removes an unnecessary step) |

**Motion & transition model**
Splash fades directly into Sign Up/Log In/Home (no slide — this is the
app's cold-start moment, a slide would imply a "previous" screen that
doesn't exist). Sign Up ↔ Log In ↔ Forgot Password use a horizontal slide
(lateral siblings in the same auth flow), matching the standard
mobile-web auth pattern documented across current login/OTP UI
references (see Research). OTP Verification presents as a forward push
(not a modal) since it's a required step, not an optional overlay. Error
states appear as an inline shake + red border on the offending field
(150ms), not a separate error screen.

**Accessibility notes**
- All inputs have visible labels (not placeholder-only) and correct
  `autocomplete`/`inputmode` attributes (email, tel, one-time-code) so
  password managers and OTP autofill work correctly.
- OTP boxes are implemented as one semantic input group for screen
  readers, not six disconnected fields (per Research: "implement the
  boxes as one semantic input whenever possible").
- Focus moves automatically to the first empty field on each screen
  load; error text is announced via `aria-live`.

**Research basis**
Read: BR01/BR09 (this module's own privacy model, which governs what
identity data is collected). Searched: OTP verification screen UX
patterns 2025 — confirmed the six-box input as the established pattern
and that platform autofill (Android SMS Retriever API, iOS autofill) is
the current best practice to minimize manual re-typing friction
([Design Studio UI/UX, "OTP Verification UI: Why Users Bail at This
Screen"](https://medium.com/@designstudiouiux/otp-verification-ui-why-users-bail-at-this-screen-b88defba900d);
[Screensdesign.com, OTP screen examples](https://screensdesign.com/articles/mobile-app-otp-verification-screen-examples/)).
Searched mobile onboarding/signup friction research, which recommends
delaying signup where possible; not fully applicable here since Milavn's
own BR01 requires an account before locality/interests can be captured,
but the finding directly supports keeping this flow to the minimum
viable field count and using a single email-or-phone field rather than
separate account-type selection
([Plotline, "Best Mobile App Onboarding Examples in 2026"](https://www.plotline.so/blog/mobile-app-onboarding-examples)).

**Assumptions**
- The underlying identity/authentication infrastructure (credential
  storage, session tokens, OTP delivery) is Common Platform Identity &
  Trust Service (`modules.md` Shared Concerns); this flow specifies only
  the screen/interaction shape Milavn's own funnel needs from it.

**Decisions**
- DEC-001 · In the context of research showing delayed/deferred signup
  reduces drop-off (e.g. TikTok's explore-before-signup pattern), facing a
  choice between that pattern and requiring signup immediately, we kept
  signup as the first required step rather than adding an unauthenticated
  "preview" mode, over deferring it, because BR01 itself frames the
  account as the prerequisite for locality/interest capture that every
  other screen depends on — deferring signup would require designing and
  building a whole separate anonymous-browsing surface the BRs never
  asked for, which is scope this module's own MVP boundary (thesis §58)
  does not include.

## UX02 — First-Run Onboarding
**Traces from:** FR001, FR002, FR003, FR081 (newly added), FR082 (newly added)
**Traced to:** UI02 (Step 4 UI)
**Priority:** P0
**Status:** Draft
**Confidence:** High

**Flow**
(From UX01's Sign Up/OTP success) → Locality entry (with Location
Permission Priming inline) → Interest selection → Language preference →
Home (Notification Permission Priming is deferred to first RSVP, not
shown here — see Decisions).

**Screen-by-screen detail**
| Screen/state | Value delivered | Contains | Primary/secondary actions | Touch/interaction model | Sentiment/tone |
|---|---|---|---|---|---|
| Locality & Location Priming | Establishes the one signal Discovery can't work without | Benefit-focused priming text, "Use my location" button, manual city/locality picker fallback | Use my location (triggers native prompt); Enter manually (secondary) | Tap; native prompt is a system overlay, not part of this screen's own layout | Encouraging, low-stakes ("this just helps us show you what's near you") |
| Interests | Personalizes Discovery from day one | Chip-style multi-select grid of interest categories (Sports, Professional, Cultural, Social, Learning, etc.) | Continue (enabled once ≥1 selected, per FR001) | Tap to toggle chips; scrollable grid | Playful, exploratory — not a form |
| Language Preference | Sets the person-level rendering language (FR002) | Three options: English / Hindi / Telugu, radio-style selection | Continue | Tap to select | Neutral, respectful of choice |

**Wireframes**
- Locality & Location Priming
  - Header: "Where are you?" + one-line benefit copy
  - Content:
    - Button: "Use my location" -> triggers native permission prompt -> on grant, auto-fills locality and advances; on deny, falls to manual picker
    - Divider: "or"
    - Picker: manual City → Zone/Locality selector
    - Button: "Continue" -> Interests (enabled once locality is set by either path)
- Interests
  - Header: "What are you into?"
  - Content:
    - Chip grid (multi-select), scrollable
    - Button: "Continue" -> Language Preference (disabled until ≥1 chip selected)
- Language Preference
  - Header: "Choose your language"
  - Content:
    - Radio list: English / Hindi / Telugu
    - Button: "Continue" -> Home (UX04)

**States**
| State | Trigger | What the user sees |
|---|---|---|
| Loading | Location lookup in progress | Inline skeleton on the manual-picker area while resolving auto-detected locality (per Research: skeleton for content-fetch, not a spinner, since layout context is known) |
| Empty | N/A | — |
| Error | Location permission denied | No error framing at all — silently reveals the manual picker; denial is a normal path, not a failure (per FR081's explicit "never blocks") |
| Success | Each step completes | Immediate advance, no interstitial confirmation |

**Motion & transition model**
Forward push (slide left) between the three onboarding steps, with a
persistent thin progress indicator at the top (3 segments) so the user
always knows how much remains — a standard, low-friction onboarding
pattern. The native location-permission prompt appears as a system
overlay on top of the Locality screen, not a custom in-app dialog (using
the actual OS prompt after the soft-ask primes it, per Research). Each
interest chip uses a springy, organic scale-bounce (not a flat color
swap) on selection — a deliberate motion choice grounded in Material 3
Expressive's own research finding that this kind of responsive,
"squishy" motion helps users register the selection faster and more
confidently than a static color change alone (see UX03's Research for
the full citation, reused here).

**Note for Step 4:** this flow is the first thing every new user ever
sees inside the product proper — its visual execution should get the
same top-tier polish investment as the P0 core-path screens (Home,
Activity Detail), not a thinner treatment, even though it is only seen
once per user.

**Accessibility notes**
- Interest chips are individually focusable and announce
  selected/unselected state.
- Progress indicator has an `aria-label` stating "Step 1 of 3" etc. for
  screen readers, not a purely visual bar.
- Manual locality picker is fully keyboard/screen-reader operable as a
  fallback for users who decline location access.

**Research basis**
Read: BR01 (minimal profile model), BR09 (approximate-locality privacy
model). Searched: mobile onboarding best practices 2026, which confirms
personalizing via a small number of smart questions and revealing
features gradually is the current standard, and that permission requests
should be tied to demonstrated value with a soft-ask before the native
prompt
([Plotline, 2026](https://www.plotline.so/blog/mobile-app-onboarding-examples);
[Appcues, "Asking nicely: 3 strategies for successful mobile permission
priming"](https://www.appcues.com/blog/mobile-permission-priming)). The
soft-ask copy pattern ("to show you what's near you, we'll need location
access") directly follows the researched benefit-focused-messaging
guidance over a bare "we need your location" framing.

**Assumptions**
- Interest category taxonomy itself is implementation-stage (per BR01
  Assumptions); the chip-grid pattern is fixed here, the actual category
  list is not.

**Decisions**
- DEC-001 · In the context of research strongly recommending permission
  requests be tied to a moment of demonstrated value rather than asked
  serially during onboarding, we deferred the Notification Permission
  Priming (FR082) out of this onboarding flow entirely, to the moment of
  a user's first RSVP (see UX08), over asking for both location and
  notifications back-to-back here, because location is provably necessary
  for the very next screen (Discovery) while notifications aren't needed
  until there's something to be notified about — asking too early risks a
  "deny" the app cannot easily recover from (iOS's one-shot native
  prompt).

## UX03 — Main Navigation Shell
**Traces from:** FR083 (newly added by this step)
**Traced to:** UI03 (Step 4 UI)
**Priority:** P0
**Status:** Draft
**Confidence:** High

**Flow**
Persistent chrome, present on every authenticated core-app screen (not
its own destination — this is the frame everything else in UX04–UX18
renders inside).

**Screen-by-screen detail**
| Screen/state | Value delivered | Contains | Primary/secondary actions | Touch/interaction model | Sentiment/tone |
|---|---|---|---|---|---|
| Bottom Navigation Bar | One-tap access to every core destination | 5 tabs: Home, Circles, Calendar, Notifications, Profile, rendered as a floating, translucent bar inset from the screen edges (not a flat opaque strip flush to the bottom) | Tap any tab -> that section's own last-visited state | Tap; active tab's indicator morphs shape (pill-shaped highlight), not just a color change | Stable, unobtrusive, but with a light layer of depth rather than flat and static |

**Wireframes**
- Bottom Navigation Bar (persistent, floating over content with a translucent/blurred surface, inset from the screen's bottom edge — content scrolls underneath it, not up to a hard stop)
  - Tab: "Home" (icon) -> UX04
  - Tab: "Circles" (icon) -> UX09
  - Tab: "Calendar" (icon) -> UX10
  - Tab: "Notifications" (icon, shows unread-count badge) -> UX12
  - Tab: "Profile" (icon) -> UX17
  - Active-tab indicator: a pill-shaped highlight that morphs/slides to sit behind whichever tab is active, rather than a static underline or plain icon-color swap

**States**
| State | Trigger | What the user sees |
|---|---|---|
| Loading | N/A (chrome, not content) | — |
| Empty | N/A | — |
| Error | N/A | — |
| Success | An unread notification exists | Notification tab shows a numeric badge |

**Motion & transition model**
Switching tabs is an instant cross-fade of content beneath the persistent
bar (the bar itself never moves or re-renders). The active-tab pill
indicator uses a springy, organic morph/slide (overshoot-and-settle, not
a linear ease) into its new position — a deliberate, specific choice, not
a generic transition, matching Material 3 Expressive's own documented
"tabs now change shape to show highlighted states" pattern, which its own
research shows helps users locate the active section faster, not merely
look more polished. The bar's translucent surface subtly reveals a blur
of whatever content scrolls beneath it, consistent with the layered-depth
treatment both major current platform design languages (Apple's Liquid
Glass, Material 3 Expressive) now use for persistent chrome, rather than
sitting as a flat, fully opaque strip.

**Accessibility notes**
- Each tab has a text label alongside its icon (not icon-only), and
  `aria-current="page"` on the active tab.
- Minimum 44×44pt touch target per tab, per standard mobile touch-target
  guidance.
- The bar's translucency must never drop content-vs-chrome contrast below
  accessible thresholds — Step 4 must verify contrast against the busiest
  realistic background content, not just an empty/light background.

**Research basis**

hamburger/drawer pattern for this kind of app
([Meetup Blog, new design 2025](https://www.meetup.com/blog/new-design-2025/)).
On second, critical review specifically for currency, searched Material 3
Expressive (released May 2025) directly and found its shape-morphing tab
indicators and "springy" motion are backed by 46 studies and 18,000+
participants showing users spot key interface elements up to four times
faster than with flat Material 3
([Dezeen, "Google ushers in age of 'expressive' interfaces," May 2025](https://www.dezeen.com/2025/05/28/google-ushers-in-age-of-expressive-interfaces-with-material-design-update/);
[Supercharge Design, "Material 3 Expressive"](https://supercharge.design/blog/material-3-expressive)).
Also searched Apple's Liquid Glass (announced WWDC, June 2025), whose
translucent, depth-aware persistent-chrome treatment is now the
cross-platform Apple design language and directly informs this bar's
floating/translucent treatment, adapted for web per its own documented
constraints (blur and translucency are reproducible on the web;
real-time refraction and motion-reactive specular highlights are not)
([Wikipedia, "Liquid Glass"](https://en.wikipedia.org/wiki/Liquid_Glass);
[The Plus Addons, "Liquid Glass in 2026... How Close CSS Can Get"](https://theplusaddons.com/blog/liquid-glass-ui/)).

**Assumptions**
- None beyond the Screen inventory's own priority reasoning.

**Decisions**
- DEC-001 · In the context of the thesis naming four discovery modes

  chose a 5-tab bottom bar (Home/Circles/Calendar/Notifications/Profile)
  over a 4-tab or drawer-based model, to keep every primary destination
  one tap away without overloading the bar past the point mobile bottom
  navigation stays usable, accepting that Map/Search live as sub-modes
  inside Home/Discovery (UX05) rather than as their own top-level tabs.
- DEC-002 · In the context of a second, critical review finding this
  bar's original flat/opaque, static-highlight treatment reads as dated

  genuine current research (not merely aesthetic preference) and are
  achievable on the web (blur/translucency) even where the fuller native
  effect (real-time refraction) is not — the exact blur/opacity/token
  values are Step 4's job; this Step fixes only that the bar must be
  designed as a floating, depth-aware surface, not a flat one.
