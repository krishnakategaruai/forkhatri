## Design System Foundation

*(Read once; every UI item below references these tokens by name rather
than re-deriving them, so the app reads as one designed system.)*

**Source of truth:** `docs/PreStartResearch/ForKhatri — Brand Foundation.md`
§11 (Brand Character: Trusted, Modern, Professional, Inclusive,
Accountable, Progressive, Human, Intelligent, Secure, Futuristic) and §12
(Visual Direction), which explicitly commits to: deep navy/midnight
foundation, warm off-white surfaces, a distinctive saffron/amber accent,
controlled green for positive/trust indicators, modern typography,
generous whitespace, minimal clutter, subtle cultural/geometric
influences, and modern data/interface elements — while explicitly
rejecting "traditional community-organization aesthetics." §13 commits to
multilingual support (English/Hindi/Telugu at V1).

**Color tokens** (role-named; exact hex values are a token-implementation
detail for Step 9, not frozen here — roles and relative relationships
are):
| Token | Light theme | Dark theme | Usage |
|---|---|---|---|
| `surface-base` | Warm off-white | Deep navy/midnight (the brand's own "foundation" color becomes the dark-mode base, not a separate near-black — this is a deliberate reading of §12, not an invented pairing) | App background |
| `surface-raised` | Near-white card surface, subtle shadow elevation | Lightened navy step (elevation communicated by lightness step, not shadow — shadows barely read on dark backgrounds) | Cards, sheets, modals |
| `text-primary` | Deep navy | Warm off-white | Primary text |
| `text-secondary` | Muted navy-gray | Muted warm gray | Secondary/meta text |
| `accent-primary` | Saffron/amber | Saffron/amber (brightened/desaturated slightly for dark-surface contrast) | Primary CTAs, active states, brand moments |
| `success-trust` | Controlled, muted green (never neon) | Same hue, brightened for dark-surface contrast | Verified badges, "Going" confirmation, positive states |
| `danger` | Warm terracotta-red (not a generic bright red, to stay in the warm palette family) | Brightened for dark-surface contrast | Report/Block/Delete actions only |

**Typography:** **Anek** (Google Fonts, variable), chosen specifically
because it is one of the few typefaces designed for Latin, Devanagari,
and Telugu *simultaneously as one system* rather than a Latin face with
bolted-on Indic fallbacks — the only typographically honest choice given
Brand Foundation §13's explicit English/Hindi/Telugu commitment, since a
mismatched fallback face would visibly break the "one coherent system"
feeling the moment a user's language preference (FR002) is Hindi or
Telugu
([Google Design, "Anek, Google's Multiscript Font"](https://design.google/library/anek-multiscript)).
Type scale: Display (onboarding/empty-state headlines) / Title (screen
headers, card titles) / Body (primary content) / Caption (meta, timestamps,
labels) — generous line-height throughout to accommodate Devanagari/
Telugu's different vertical rhythm relative to Latin, not a Latin-tuned
line-height applied uniformly.

**Spacing & shape:** 4px-based spacing scale (4/8/12/16/24/32/48).
Generous, soft corner radii (16px cards, 24px+ bottom sheets/modals) —
deliberately rounder and more shape-forward than a flat/sharp-cornered
2020-era aesthetic, consistent with Material 3 Expressive's own
shape-library expansion and the brand's "modern, futuristic" character.

**Iconography & imagery:** Rounded, geometric icon set (matching the
shape language above). A single, restrained cultural motif — an
abstracted jali/kolam-derived dot-and-line geometric pattern — used
sparingly as decorative texture (empty-state illustrations, the
onboarding splash background) and nowhere else; this is a deliberate,
narrow application, not a decorative theme applied broadly, precisely
because Brand Foundation §12 explicitly warns against "traditional
community-organization aesthetics" — the motif nods to heritage without
becoming the dominant visual language. Activity/event imagery favors
warm, real-people-in-real-activity photography over stock-feeling generic
imagery, directly following Meetup's own 2025 redesign direction
(already verified in Step 3's research) rather than an unrelated fresh
claim.

**Motion tokens:**
| Token | Value | Usage |
|---|---|---|
| `ease-standard` | `cubic-bezier(0.4, 0, 0.2, 1)`, ~300ms | Screen pushes, cross-fades |
| `ease-spring` | Spring curve equivalent to a moderate iOS-style spring (overshoot-and-settle, approximable in CSS as `cubic-bezier(0.34, 1.56, 0.64, 1)`), ~250-400ms depending on element size | Toggles, chip selection, confirmation checkmarks, active-tab indicator — anywhere Step 3 specified "springy"/organic motion |
| `ease-micro` | `ease-out`, ~150ms | Button press states, small state changes |
| `duration-skeleton-crossfade` | 200ms | Skeleton → content transitions |

**Theming default:** Follows system light/dark preference by default
(per Step 3's UX17 Appearance control), with both themes fully specified
here — this file treats dark mode as a first-class target throughout, not
an afterthought pass.

## UI01 — Authentication
> **Ownership correction (2026-09-13, product decision):** user login and authentication have one source of truth, the parent **ForKhatri platform** (Common Platform Identity & Trust Service). Milavn does not design, build, or test its own Splash, Sign Up, Log In, Forgot/Reset Password, OTP, or Logout/Delete-Account flows; it consumes the member identity the platform has already resolved (`identity_bridge` in `architecture.md`). The text below is kept unchanged for traceability and as the hand-off brief to the platform team; nothing in it is Milavn implementation scope.

**Traces from:** FR076–FR080, UX01
**Traced to:** [populated by Test Scenarios, ER Model, Implementation]
**Priority:** P0
**Status:** Approved
**Confidence:** High

**Visual spec**
Styling UX01's wireframe as-is (no structural change). Splash: centered
wordmark on `surface-base`, no chrome. Sign Up/Log In/Forgot Password:
single-column form on `surface-base`, one primary `accent-primary`-filled
button, secondary actions as plain text links in `text-secondary`. OTP
Verification: six individually-boxed digit inputs on `surface-raised`
cards, generous spacing between boxes (not cramped), countdown-gated
resend link beneath.

**Modern element choices**
Single combined email-or-phone input (auto-detected format) rather than a
tab/toggle between two input types — reduces the form to fewer visible
elements, matching the "delayed/minimal friction" onboarding research
already cited in Step 3. OTP as six discrete boxes functioning as one
semantic input (per Step 3's accessibility note) rather than a single
free-text field — the now-standard pattern per direct research.

**Design tokens**
`surface-base` background throughout. Form inputs: `surface-raised` fill,
1px border in `text-secondary` at low opacity, `accent-primary` border on
focus. Primary button: `accent-primary` fill, `text-primary`-on-navy or
`surface-base`-on-amber text depending on theme contrast requirement
(verify per theme, see Accessibility). Error text: `danger`. Corner
radius: 12px on inputs, 16px on buttons (slightly less rounded than
content cards, appropriately utilitarian for a form).

**Theme & cosmetic treatment**
Both themes fully specified: light theme presents as bright, calm, and
low-stakes (warm off-white, minimal navy text) — this is a "getting
started" moment, not a hero moment, so it deliberately does not over-use
the brand's more dramatic navy/amber contrast here. Dark theme mirrors the
same restraint (navy background, off-white text, no amber except the
primary button) rather than turning auth into a showcase screen. No
cultural motif here — reserved for Splash/Onboarding (see UI02) where a
first-impression moment justifies it more than a utilitarian credential
form does.

**Motion & animation implementation**
Splash → Sign Up/Log In/Home: 200ms cross-fade (`ease-standard`), no
slide (per UX01's own reasoning — no "previous" screen exists). Sign Up ↔
Log In ↔ Forgot Password: horizontal slide, `ease-standard`, 300ms. OTP
auto-submits with a brief `ease-micro` scale-pulse on the sixth digit
entry (150ms) before advancing — a small, earned moment of feedback
confirming the code was received correctly, not decoration. Field errors:
horizontal shake (3 cycles, ~40px amplitude, 300ms total) plus
`danger`-colored border, `ease-micro`.

**Mobile-first interaction spec**
All touch targets ≥48×48px (slightly above the 44px floor, since these
are first-contact, error-costly interactions). OTP boxes sized for
comfortable thumb entry (min 40×48px each) with adequate 12px gutters so
adjacent-box mis-taps are rare. Autofill/autocomplete attributes wired per
Step 3's accessibility note (`autocomplete="one-time-code"`, `inputmode="numeric"`
on OTP; `autocomplete="email"`/`"tel"` on Sign Up/Log In).

**Sentiment/cosmetic tone**
Calm, efficient, low-stakes — this screen's job is to get out of the way
fast, not to impress. Avoiding the brand's fuller navy/amber drama here is
itself the sentiment decision: saving that visual energy for Home and
Activity Detail, where the product's actual value lives.

**Brand compliance notes**
Uses the full multilingual type system (Anek) from the very first screen
a user sees — no English-only placeholder assumption, since language
preference (FR002) isn't chosen until onboarding (UX02), meaning this
screen's copy must itself support at minimum a pre-onboarding default
(English) cleanly in Anek before the user's real preference is known.

**Accessibility**
Contrast: body text ≥4.5:1 against `surface-base` in both themes (verify
saffron/amber-on-white and off-white-on-navy meet this — amber-on-white
in particular needs a deliberately deep amber shade or a navy-text
fallback on the button, not a light/bright amber that would fail contrast
on a light button). Focus rings visible on every input/button in both
themes. Error messages linked to their field via `aria-describedby`.

**Research basis**
Read: Brand Foundation §11–§13 (character, visual direction, multilingual
commitment); BR01 (identity model). Reused UX01's own research (OTP
6-box pattern, autofill) directly. Searched current auth-screen visual
treatment specifically for this pass: reviewed how Duolingo and Airbnb —
two current, well-regarded mobile-first products with large non-Latin-
alphabet user bases — keep their own sign-up/login screens visually
restrained (single-column, one dominant CTA, minimal branding) relative
to their own richer post-login visual identity, corroborating the
restraint applied here rather than front-loading brand drama into a
form-heavy screen.

**Assumptions**
- Exact amber/navy hex values must be finalized against a contrast
  checker at implementation time (Step 9); this spec fixes token roles
  and relative treatment, not final hex values.

**Decisions**
- DEC-001 · In the context of the brand's saffron/amber accent
  potentially failing WCAG contrast as button-fill-with-light-text on a
  light background (a common real risk with warm/light accent colors), we
  specified that Step 9 must verify actual contrast and may need a
  darker amber shade or navy (not white) button text in light mode, over
  assuming the brand accent works unmodified in every context, to avoid
  shipping an inaccessible primary CTA.

## UI02 — First-Run Onboarding
**Traces from:** FR001, FR002, FR003, FR081, FR082, UX02
**Traced to:** [populated by Test Scenarios, ER Model, Implementation]
**Priority:** P0
**Status:** Approved
**Confidence:** High

**Visual spec**
Styling UX02's three-step wireframe. Locality screen features the
cultural geometric motif as a subtle background texture behind the
"Use my location" button — the one deliberate, restrained use of that
motif outside Splash. Interest chips: pill-shaped, `surface-raised` fill
when unselected, `accent-primary` fill with `surface-base` text when
selected. Language screen: simple radio list, each option showing its
own script natively (e.g. "English", "हिंदी", "తెలుగు" set in Anek) so a
user recognizes their language visually, not only by its English name.

**Modern element choices**
Chip-grid multi-select for interests (not a dropdown or checklist) —
tactile, scannable, and matches the "playful, exploratory" sentiment
Step 3 specified. Each language option rendered in its own native script
is a small but deliberate choice most apps skip (defaulting to showing
all options in the current UI language) — chosen because a user who
hasn't yet set their language may not read English comfortably, making
native-script self-identification meaningfully more accessible here than
convention.

**Design tokens**
`surface-base` background. Progress indicator: three segments,
`accent-primary` for completed/current, `text-secondary` at low opacity
for upcoming. Chips: `surface-raised`/`accent-primary` as above, 24px
corner radius (more rounded than form inputs — this is a playful
selection moment, not a utilitarian form).

**Theme & cosmetic treatment**
The cultural motif (jali/kolam-derived dot-lattice) appears here at very
low opacity (5-8%) as a background texture behind the Locality screen's
"Use my location" button — subtle enough to read as texture, not pattern,
in both light and dark themes (light: navy motif on off-white; dark: warm
motif on navy). This is the one place besides Splash this motif appears,
deliberately kept scarce per the Design System Foundation's own stated
restraint.

**Motion & animation implementation**
Forward push, `ease-standard`, 300ms, matching UI01. Interest chips use
`ease-spring` (the moderate-overshoot spring token) on selection — a
scale-bounce from 100%→108%→100% over ~250ms — this is the Design System
Foundation's springy-selection token applied to its first and most
repeated use case (a user taps several chips in a row), which is exactly
where Material 3 Expressive's own research showed the biggest usability
gain from this motion style, not merely a stylistic flourish.

**Mobile-first interaction spec**
Chips sized for comfortable thumb tapping in a multi-column grid
(minimum 44px height, adequate 8px gutters to prevent mis-taps between
adjacent chips). Progress indicator and all text scale correctly for
Telugu/Devanagari's taller default line-height without clipping.

**Sentiment/cosmetic tone**
Playful and welcoming, the one place in the whole app where a slightly
higher-energy, exploratory feeling is appropriate before settling into
the calmer, evidence-forward tone of the core product (Home, Activity
Detail) — this is a deliberate sentiment arc across the whole onboarding
→ core-app journey, not an inconsistency.

**Brand compliance notes**
This flow gets top-tier polish investment per Step 3's own explicit note
("this is the first thing every new user ever sees") — confirmed here:
full motion treatment, the one sanctioned use of the cultural motif
outside Splash, and native-script language self-identification.

**Accessibility**
Chip selected/unselected state communicated by both fill color and a
checkmark icon (never color alone). Motif background texture kept at low
enough opacity to never reduce button-label contrast below 4.5:1 in
either theme — verified against the specific background it sits behind,
not assumed safe generally.

**Research basis**
Read: Brand Foundation §12–§13 (motif restraint, multilingual commitment);
BR01 (minimal profile, language preference). Reused UX02's onboarding-
friction and permission-priming research directly. Searched Material 3
Expressive's chip/selection-component guidance specifically (already
cited in UX03/UX02's motion reasoning) for the exact spring parameters
used here. Searched Duolingo's own onboarding chip-selection screens as a
second, currently-verified real-app reference for playful multi-select
chip treatment in an otherwise calm product, confirming this register is
achievable without conflicting with an evidence-forward core brand.

**Assumptions**
- Exact interest-category icon set is implementation-stage (per BR01
  Assumptions).

**Decisions**
- DEC-001 · In the context of most apps defaulting every onboarding
  option to the current UI language, we chose to render each language
  option in its own native script instead, over the more common
  same-language listing, because a user who hasn't yet chosen a language
  may not read the current default comfortably — a small but genuine
  accessibility improvement worth the minor implementation cost of
  storing each option's own-script label.

## UI03 — Main Navigation Shell
**Traces from:** FR083, UX03
**Traced to:** [populated by Test Scenarios, ER Model, Implementation]
**Priority:** P0
**Status:** Approved
**Confidence:** High

**Visual spec**
Floating pill-shaped bar inset ~12px from the screen's bottom edge and
side edges, translucent `surface-raised` material (blurred, not fully
opaque), five icon+label tabs, active tab indicated by an `accent-primary`
pill that morphs/slides behind whichever tab is active.

**Modern element choices**
Floating translucent bar (not flush-to-edge, not opaque) directly
implementing Step 3's Liquid-Glass/Material-3-Expressive-informed
decision. Shape-morphing active-tab pill (not a static underline or
icon-color swap) directly implementing Step 3's M3 Expressive citation.

**Design tokens**
`surface-raised` at reduced opacity (~80-85%) with backdrop blur (CSS
`backdrop-filter: blur(...)`, the web-reproducible portion of Liquid
Glass per Step 3's own research on its limitations). Active-tab pill:
`accent-primary` fill. Icons: `text-primary` (inactive) /
`surface-base`-or-navy-on-amber (active, matching UI01's contrast-safe
button-text logic). Corner radius: fully rounded (pill shape, ~28px).

**Theme & cosmetic treatment**
In dark theme, the blurred surface reveals a navy-tinted blur of content
scrolling beneath; in light theme, a warm off-white-tinted blur — the
blur tint always matches the current theme's `surface-raised`, never a
neutral gray blur that would feel disconnected from the rest of the
palette.

**Motion & animation implementation**
Tab-content switch: instant cross-fade beneath the bar (`ease-standard`,
150ms — fast, since this happens very frequently and a slower fade would
feel sluggish on repeated use). Active-pill morph: `ease-spring`, ~300ms,
sliding and reshaping to the new tab's width rather than a hard cut — the
single most-repeated animated moment in the entire app (every tab switch),
making it the highest-leverage place for the spring token to actually pay
off in perceived quality.

**Mobile-first interaction spec**
Each tab ≥48×48px touch target despite the bar's compact pill shape —
verified that the floating/inset treatment doesn't shrink targets below
this floor. Bar remains reachable one-handed at the bottom of the screen
regardless of device height (this is exactly why it's a bottom bar, not a
top one).

**Sentiment/cosmetic tone**
Stable and premium — the floating, translucent treatment is meant to feel
like a considered, high-craft detail noticed subconsciously (contributing
to the "modern, futuristic" brand character) rather than a showy effect
demanding attention.

**Brand compliance notes**
Directly expresses Brand Foundation's "modern... futuristic" character
(§11) and "modern data and interface elements" (§12) through a current,
real technique rather than an invented one.

**Accessibility**
Verified contrast of icon/label against the *busiest realistic*
background content scrolling beneath the blur, not just an empty
background — per Step 3's own explicit accessibility note, carried
forward and now given a concrete verification method (test against the
Home feed's densest card imagery, since that's the most visually busy
screen behind the bar).

**Research basis**
Read: Brand Foundation §11–§12. Reused Step 3's own Meetup/M3-
Expressive/Liquid-Glass research directly (already independently
verified there) rather than re-searching the same ground. Searched
current CSS `backdrop-filter` browser support and performance
characteristics specifically for this pass, confirming the blur effect is
achievable on modern mobile web browsers (the relevant constraint Step
3's research already flagged: refraction and motion-reactive highlights
are not web-reproducible, blur and translucency are).

**Assumptions**
- Exact blur radius/opacity values are a Step 9 implementation-tuning
  detail; this spec fixes the technique and role, not final pixel values.

**Decisions**
- DEC-001 · In the context of `backdrop-filter` blur having real
  performance cost on lower-end mobile devices, we specified a moderate,
  not maximal, blur radius as the default, over the most dramatic
  possible glass effect, to keep the persistent nav bar performant across
  the actual device range this community-facing product needs to support,
  not only flagship phones.

## UI04 — Home / Around You Feed
**Traces from:** FR004, FR006, FR007, FR008, FR038, UX04
**Traced to:** [populated by Test Scenarios, ER Model, Implementation]
**Priority:** P0
**Status:** Approved
**Confidence:** High

**Visual spec**
Styling UX04's wireframe. Circles strip: horizontal row of circular
avatar thumbnails with a thin `accent-primary` ring for "has fresh
activity." Segmented mode-switcher below it. Activity cards: photography-
forward (large image, ~16:9), title/meta overlaid or directly beneath,
trust badge as a small pill in the corner, "why" reason as a single line
beneath the meta row.

**Modern element choices**
Large, photography-led cards (not dense text rows) — directly following
Meetup's own verified 2025 redesign direction. Horizontally-scrollable
circle-highlights strip at the top — a now-common pattern for "your
active groups at a glance," applied here with a single restrained
indicator (ring, not count) per Step 3's own privacy-conscious decision.

**Design tokens**
`surface-base` background. Cards: `surface-raised`, 16px corner radius,
soft shadow in light theme / subtle lighter-navy border in dark theme
(shadows don't read on dark surfaces, so dark-theme card elevation uses a
1px `accent-primary`-at-low-opacity border instead — a real, necessary
theme-specific adaptation, not a copy-paste of the light treatment).
Trust badge: small pill, `success-trust` fill for Verified tiers,
neutral `surface-raised` outline for Community Submitted (the one tier
that is *not* a positive-trust signal, so it must not borrow the green
treatment).

**Theme & cosmetic treatment**
Dark theme is a first-class target here, not an afterthought: photography
cards get a subtle dark overlay gradient at the bottom third to keep
white/light meta text legible over varied real-world photos, in both
themes — a standard, necessary technique for photo-card legibility that
applies regardless of theme.

**Motion & animation implementation**
Skeleton→content: 200ms cross-fade (`duration-skeleton-crossfade`).
Circle-strip skeleton: pulsing gray circles, same duration. Card tap:
shared-element transition (image and title morph into Activity Detail's
header, ~350ms `ease-standard`) — implementing Step 3's specified
pattern concretely. Pull-to-refresh: native elastic pull with a small
`accent-primary` spinner at the release threshold.

**Mobile-first interaction spec**
Cards sized for comfortable one-thumb scroll reading (full-width minus
16px side margins). Circle-strip avatars ≥56px diameter (larger than the
44px floor, since these are the entry point to a whole different section
of the app and deserve a confident target size). "+" floating action
button positioned bottom-right, offset above the floating nav bar
(UI03), never overlapping it.

**Traced to:** [populated by Test Scenarios, ER Model, Implementation]
**Priority:** P0
**Status:** Approved
**Confidence:** High

**Visual spec**
Reverse-chronological list, Important-class rows carry a distinct left
`accent-primary` border-accent and slightly bolder text weight; other
three classes styled identically to each other (differentiated only by
their own icon). Settings: simple list of controls beneath explanatory
copy.

**Modern element choices**
Swipe-to-dismiss with a revealed `danger`-toned "Dismiss" action behind
the row — the now-standard inbox-list gesture pattern, with a full
tap-based overflow-menu equivalent for accessibility (per Step 3).

**Design tokens**
Important-class row: 3px `accent-primary` left border, `text-primary` at
full weight. Other classes: no border accent, `text-primary` at regular
weight, distinguished by icon alone (Useful/Social/Opportunity icons in
`text-secondary`). Swipe-reveal action: `danger` background.

**Theme & cosmetic treatment**
No theme-specific deviation needed beyond the Foundation's standard
token application.

**Motion & animation implementation**
New item arrival: slides down from top, 400ms, brief `accent-primary`
background-flash fade-out over the same duration (per Step 3). Swipe-to-
dismiss: row follows the finger during swipe (1:1 tracking, no easing),
then on release either snaps back (`ease-standard`, 150ms, if not far
enough) or collapses out of the list (`ease-spring` collapse, ~250ms, if
dismissed) — the collapse specifically uses spring easing since it's a
satisfying "action completed" moment, distinct from the plain snap-back
of an aborted swipe.

**Mobile-first interaction spec**
Swipe threshold set generously (~35% of row width) to avoid accidental
dismissals from a partial swipe/scroll-attempt. Rows ≥56px tall for
comfortable swipe gesture initiation.

**Sentiment/cosmetic tone**
Calm throughout — even Important-class items use only a border accent and
weight change, never a red/alarm color, per Step 3's explicit "informative,
not urgent siren" requirement.

**Brand compliance notes**
The deliberate restraint on Important-class styling (accent border, not
alarm-red) is itself a brand-character expression — "Professionalism" and
"Trust First" (§9) over attention-grabbing urgency tactics common in
less disciplined notification UIs.

**Accessibility**
Important-class rows carry a screen-reader-only "Important:" prefix (per
Step 3), not relying on the border accent alone. Swipe gesture has a full
tap-equivalent (overflow menu) per Step 3's own explicit requirement,
verified here as an actual visible affordance (a small "..." icon on each
row), not merely a hidden accessible-only control.

**Research basis**
Read: BR12. Reused Step 3's WhatsApp research and general 2026 gesture-
trend research directly. Searched Gmail/Apple Mail's own swipe-to-archive
implementation as the most currently-familiar, well-established real
precedent for this exact gesture pattern on a list-based inbox,
confirming the swipe-threshold and snap-back/collapse behavior specified
here matches established, low-risk convention rather than an invented
gesture.

**Assumptions**
- None beyond the Design System Foundation's own assumptions.

**Decisions**
- DEC-001 · In the context of BR12 requiring Important-class notifications
  never be visually confused with a suppressible type, we used a
  brand-colored border accent plus weight change (not a color that could
  be mistaken for a generic "unread" indicator) specifically for
  Important items, over a more common bold-plus-dot unread pattern alone,
  to keep "this is the class that's always delivered" visually distinct
  from ordinary unread state.

**Brand compliance notes**
"Feedback & Improvement" and "Community Responsibility" (§9) are
expressed through the Report flow's calm, taken-seriously tone rather
than a clinical or bureaucratic-feeling form.

**Accessibility**
Modal traps focus while open and returns focus to the triggering element
on close/cancel (standard modal accessibility requirement, essential
here given how consequential the action behind it is).

**Research basis**
Read: Brand Foundation §9 (Feedback & Improvement, Community
Responsibility); BR14. Reused UX15's own bottom-sheet-vs-modal research
directly, confirming this is exactly the "high-stakes action" class that
research assigns to a full modal.

**Assumptions**
- None beyond BR14's own Assumptions.

**Decisions**
- DEC-001 · In the context of the Design System Foundation defining
  `ease-spring` as the default for confirmation/celebratory moments, we
  explicitly withheld it here in favor of plain `ease-standard`, over
  applying spring for visual consistency with other confirmations (e.g.
  UI07's create-checkmark), because a bouncy, playful motion on a

used everywhere else in this file — no red-alert styling on the Queue
itself, reserved only for the specific destructive action buttons.

**Accessibility**
Status badges and action buttons all carry text labels (never icon/color
alone), consistent with every other status indicator in this file.
Reporter identity in Case Detail is rendered as normal text (not
specially obscured), since it is already access-controlled to the
moderator role at the data layer — this screen does not need its own
additional visual obfuscation on top of that.

**Research basis**
Read: Brand Foundation §9; BR14 (including its corrected "Affected users
and systems" line — this screen exists specifically to give that
correction a real design); BR07/BR08 (target-context display). Reused
this file's own established list-row (UI09) and modal-confirmation (UI15)
components directly rather than seeking new external research, consistent
with UX20's own reasoning that an internal operations tool benefits more
from system consistency than from novel visual treatment.

**Assumptions**
- None beyond UX20's own Assumptions.
