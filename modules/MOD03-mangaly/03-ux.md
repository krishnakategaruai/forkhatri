## Global UX foundations (apply to every flow below; not repeated per item except where a flow needs a specific addition)

**Why this section exists:** the agent brief for this file requires "one coherent app, not independently-invented fragments." These are the cross-cutting decisions every one of the 30 flows below was designed against, so a reviewer can tell when a flow is following house style versus deviating for a real reason.

**Navigation model.** A persistent bottom tab bar (5 destinations) is the primary navigation surface for an authenticated user acting in their own candidate context: **Discover** (compass icon, default landing tab), **Connections** (heart-handshake icon — connection requests + active explorations), **Circle** (people icon — Home Circle hub), **Messages** (chat-bubble icon — conversation list), **Profile** (person icon — own profile + entry to Settings). A top header persists above the tab bar on every screen: app wordmark/logo at left, a **Home Circle context chip** at center-left (only shown once a user participates in more than one matrimonial context — see UX06), and a **notification bell** at right opening the Notification Inbox (UX07) as a full-screen push. This is a deliberate departure from swipe-card dating-app navigation (Tinder/Bumble's single-card stack) toward the tab-bar-plus-feed pattern used by LinkedIn, Airbnb, and Hinge's own non-swipe "Discover" grid — chosen because Mangaly's own scope explicitly rejects "swipe/dating-style browsing as the core interaction model" (BR06 "Out of scope") and needs room for five genuinely different first-class capability areas (browse, decide, family, talk, self), not one.

**Terminology (plain-language, never RBAC-speak, per M01-D).** "Home Circle" (family group) · "Suggest" (never "recommend to" in a way that implies algorithmic push) · "Connect" / "Connection request" (never "match request") · "Explore" for the accepted-but-undecided state ("You're now exploring a connection with Ananya") · "Share" for Selective Sharing actions · "Evidence" (never "verification score" or "trust score" — BR08/FR039 forbid this outright) · capability statements are always phrased as what a person *can do* ("Mom can suggest profiles for you"), never as a permission/role label, per M01-D §3–4 and its explicit rejection of "large user-facing RBAC permission matrices."

**Motion vocabulary (named once, cited per flow as "[pattern name]").**
- **Tab cross-fade** — switching bottom-tab destinations cross-fades content in place, no directional slide (Instagram/YouTube/LinkedIn tab-bar convention — tabs are siblings, not a stack, so a slide would wrongly imply hierarchy).
- **Stack push/pop** — drilling from a list into a detail (Discovery feed → profile detail; Notification Inbox → the referenced screen) slides the new screen in from the right; the OS back-gesture/edge-swipe slides it back out (standard iOS/Android/Material stack navigation).
- **Bottom sheet** — any contextual action that doesn't warrant leaving the current screen (Suggest to Family, Report, Share a category, the Home Circle context switcher, Filters) slides up from the bottom over a dimmed scrim and is dismissible by drag-down or scrim-tap (Instagram's share sheet, Bumble's report sheet, Airbnb's filter sheet).
- **Full-screen takeover** — high-commitment, hard-to-undo moments (Sign-Up, Onboarding, reviewing an incoming Connection Request, filing a Safety Report, confirming Account Deletion) push in as a full-screen modal with an explicit "X"/back control rather than being swipe-dismissible, so a consequential action is never exited by an accidental gesture.
- **Success confirmation** — a small centered checkmark micro-animation plus a light haptic tap, then an auto-dismissing toast/snackbar — never a full-screen "It's a Match!"-style celebration modal (Material Design snackbar pattern; deliberately not Tinder/Bumble's confetti-burst pattern, which reads as gamified rather than trustworthy per the Brand Foundation's "not another social-media platform optimized for... virality").
- **Loading** — skeleton screens for any content list (Discovery, Messages, Notification Inbox, Circle feed), matching the Instagram/LinkedIn feed-loading convention; a small inline spinner only for a button mid-submission (label replaced by spinner, button stays the same size to avoid layout shift).
- **Privacy-mode cue** — opening a private conversation thread (UX21) shows a brief, calm cue (a small shield/lock glyph animating into the thread header, which then persists as a small "Private · Limited-Retention" tag) rather than Instagram Vanish Mode's full-screen darkening — a deliberately quieter treatment consistent with this product's "calm and authoritative, not clinical or alarming" register for trust/safety moments.
- **Reduced motion** — every pattern above collapses to an instant cut (no slide/fade duration) when the OS-level "reduce motion" accessibility setting is on.

**Sentiment/tone baseline (from `ForKhatri — Brand Foundation.md` §11, §15).** Trusted, modern, professional, human, secure — "not another social-media platform optimized for Followers · Likes · Virality." Concretely: no swipe-card gamification, no celebratory confetti on a match, no urgent/red-alarm styling on profile-completeness nudges (encouraging language only — "Add a photo to help your profile stand out" never "Your profile is incomplete!"), and no bureaucratic/legalistic tone on accountability or verification surfaces despite their serious subject matter — copy reads like a trusted family advisor, not a compliance form or a dating-app growth-hack banner.

**Global accessibility baseline (referenced per flow as "per Global baseline," with flow-specific additions noted separately).**
- Every interactive control meets a minimum touch target of 44×44pt (iOS HIG) / 48×48dp (Material) regardless of visual size.
- Every icon-only control (tab bar icons, bell, back arrows, context-switcher chip) carries a screen-reader label describing its action, not its icon ("Open notifications," not "bell icon").
- Color is never the sole carrier of meaning (verification-layer status, request state, safety severity all pair an icon and/or text label with any color Step 4 selects).
- Focus order follows visual top-to-bottom/left-to-right reading order on every screen; opening a bottom sheet or full-screen takeover traps focus inside it and returns focus to the triggering control on close.
- Every form field has a persistent visible label (not placeholder-only text) with inline errors linked via `aria-describedby`.
- Layout tolerates OS text-scaling up to at least 200% without clipping or overlap — material given this product's named user group explicitly includes parents, who skew older than a typical dating-app user.
- All motion respects the OS "reduce motion" setting (see Motion vocabulary above).

**Research grounding used across this entire file (cited again per-flow where most relevant, not repeated in full each time):** live searches on mobile onboarding/signup UX (2025–2026), OTP verification UX, permission-priming patterns, Hinge/Bumble profile-creation and prompt design, Shaadi.com/BharatMatrimony profile/verification conventions, Life360/Google Family Group invite patterns, Hinge's "Most Compatible" explanation design, Tinder Face Check/Bumble photo-verification trust badges, LinkedIn connection-request accept/decline conventions, Snapchat/Instagram ephemeral-messaging UX, Airbnb's pre-booking contact-masking pattern, Bumble's report/block/safety-center flow, Bumble Snooze Mode/Hinge Pause Mode, Tinder "Share My Date"/Bumble "Share Date" real-world-meeting safety features, trust-and-safety admin-console/case-queue UX patterns, testimonial-consent-capture UX, bottom-tab/account-switcher patterns, and empty-state/notification-inbox design conventions — plus this project's own prior research already recorded in `01-business-requirements.md` (Hinge Most Compatible, Shaadi.com/BharatMatrimony evidence-layer verification, Tinder/Bumble graduated safety response, CMU/Tepper popularity-bias findings) and the Mangaly M01 dossiers (`docs/PreStartResearch/Mangaly_M01_*.docx`, extracted and read in full for this pass).

**Flow**
App icon tap → Splash screen (brief, branded) → session check runs in background → routes to exactly one of: Onboarding (UX02, first-ever launch), Login (UX03, expired/no session), or Main Shell (UX06, valid session) → exit (splash never reappears mid-session).

**Screen-by-screen detail**
| Screen/state | Value delivered | Contains | Primary/secondary actions | Touch/interaction model | Sentiment/tone |
|---|---|---|---|---|---|
| Splash | Confirms the app opened correctly; buys time for session check without feeling stuck | Wordmark/logo, no interactive controls | None (auto-advances) | No touch input accepted or needed | Calm, confident — a brief breath, not a loading ordeal |

**Wireframes**
- Splash
  - Content: centered app wordmark/logo, no header, no tab bar (this is the one screen with neither)
  - (no buttons — fully automatic)

**States**
| State | Trigger | What the user sees |
|---|---|---|
| Loading | App cold start | Splash screen, session check in flight (skeleton not applicable — single branded screen) |
| Success — first-ever launch | No session ever existed on this device/account | Routes to Onboarding (UX02) |
| Success — valid session | Recent, valid session token found | Routes to Main Shell (UX06), skipping onboarding/login entirely |
| Error/failure | Session check cannot complete (network failure, expired/invalid token) within a bounded wait (per FR090's acceptance criteria) | Routes to Login (UX03) with a plain-language reason ("Please sign in again") — never an indefinite blank screen |

**Motion & transition model**
Splash fades in instantly on tap (no slide, it's the app's entry point, not a stack push). Departure to the next screen is a simple cross-fade — never a slide, since splash is not conceptually "before" or "after" the destination in a spatial sense. If the session check exceeds the bounded wait, a subtle fade-to-Login occurs rather than a jarring cut. Respects reduced-motion (instant cut for both entry and exit).

**Accessibility notes**
- Per Global baseline. Splash carries no interactive elements, so no focus order applies; screen-reader announces the app name once on launch and nothing else (avoids an empty, confusing announcement).
- The bounded-wait fallback must not rely on a visual-only cue — if a timeout message appears at all, it is announced to screen readers, not just shown.

**Research basis**
Read: FR090 and its Intent (this step's own addition); BR01's Worth check ("the floor of the product"). Live research: mobile app onboarding/launch UX best practices (2025–2026) — the widely-cited "apps lose 77% of users within 3 days without a good first-time experience" finding informed keeping this screen deliberately minimal rather than adding a branded animation that delays routing. No named comparable app needed a dedicated study here — a splash/bootstrap screen is close to universal mobile convention (WhatsApp, Instagram, LinkedIn all use a near-instant branded splash before routing), cited generically rather than to one specific app.

**Assumptions**
Session/token validity mechanics are Common Platform infrastructure (per FR090's own Assumptions); this flow only fixes Mangaly's routing behavior once that check resolves.

**Decisions** (append-only)
- Chose cross-fade over any branded loading animation, to keep time-to-first-real-screen as short as possible, per the onboarding-retention research above.

| Previously declined, re-offered later | User later takes an action where the permission would newly help, having declined before | A single, non-repetitive re-offer may appear once at a materially different moment (e.g. switching device or reinstalling), never a nag loop |

**Traces from:** FR102 (newly added by this step — no parent BR; pure technical necessity, stated plainly in FR102's own Intent)

**Motion & transition model**
Mark-search-concluded is a Global stack push from Profile edit hub or Settings (a meaningful, considered action, but reversible, so it doesn't need full-screen-takeover weight). Reactivate is a Global bottom sheet (a lighter, welcoming, low-friction re-entry action, deliberately less ceremonious than concluding, to avoid making a candidate feel they need to justify coming back).

**Accessibility notes**
- Per Global baseline, plus: the "Search concluded" banner's state and the "Reactivate" control are both part of the same accessible region, read together, so a screen-reader user immediately understands both the current state and the available action.

**Research basis**
Read: FR079–FR081 and BR18 in full, including its own honest note that this BR has no source-document citation and was written from first principles against the module's own stated purpose (a genuine gap the Product Manager identified, not an invented one). Live research: Bumble's Snooze Mode and Hinge's Pause Mode (already cited in UX15) are the closest researched analogues for "temporarily or permanently step back from active matching without losing your account," though both are framed as *pausing*, not *concluding a successful outcome* — this flow deliberately borrows their "no data loss, easy to reverse" mechanics while adding the celebratory/neutral reason-framing that a matrimonial *lifecycle* conclusion needs and a simple dating-app pause does not.

**Assumptions**
None beyond BR18's own.

**Decisions** (append-only)

## UX29 — Success Story Capture & Consent
**Traces from:** FR082, FR083, FR084 — parent BR19 (Success Story Capture & Consent)
**Traced to:** [populated by UI/Test Scenarios agents]
**Priority:** P2
**Status:** Ready for Review
**Confidence:** Medium (matches FR082/FR083/FR084's own Medium confidence — Could-priority, no source-document citation per BR19)

**Flow**
Entry: triggered only after a match has concluded (UX28) with both parties marking "engaged"/"married" — Mangaly invites both to share a success story. Steps: each invited candidate independently receives their own Story-invitation screen → each separately completes their own Story-consent form (what they're comfortable sharing) → if and only if every involved party consents, a Story preview/approval screen lets each party see and approve the exact final content before anything is used. **Screen-by-screen detail**
| Screen/state | Value delivered | Contains | Primary/secondary actions | Touch/interaction model | Sentiment/tone |

**Accessibility notes**
- Per Global baseline, plus: each party's own approval status on the Story preview screen is exposed individually and clearly ("Your approval: Approved" / "[Other party]'s approval: Waiting"), so a screen-reader user isn't left guessing whose action is still needed.

**Research basis**
Read: FR082–FR084 and BR19 in full, including its explicit "never required, never assumed from BR18's conclusion action" Constraint. **Assumptions**
Publication channel (in-app, website, social) is a later marketing/distribution decision outside this flow's scope (per BR19's own Assumptions); this flow only fixes that consent can be captured and a story can exist as data.

**Decisions** (append-only)
- Chose to require both parties' fully independent consent (neither can see or influence the other's decision mid-process) rather than a single shared consent step, directly reflecting BR19's own "explicit, specific, revocable consent from every candidate involved" DEC-001 rather than a lighter-weight single-consent pattern more typical of ordinary testimonial tools.

**Assumptions**
