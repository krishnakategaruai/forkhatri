# Parent Application UX

## Revision history

| Date | Change | Reason |

## UX01 — Shared entry and session state

The first view establishes ForKhatri as the product. A member with a valid
session goes straight to the hub, or straight to the module named in a safe
`return_to`. A signed-out member sees one conversational card. When arriving
from a module, the card names it ("Sign in to continue to Milavn").

## UX02 — Conversational sign-in

One question at a time, each step replacing the last with a transition:

1. "Your phone number or email" — a 10-digit Indian mobile is accepted without `+91`.
2. "Enter the 6-digit code sent to +91•••••43210" — auto-submits on the sixth digit; resend becomes available when the countdown ends; a wrong code keeps the member on the step with remaining attempts implied, and an expired or exhausted code offers a fresh one.
3. New members only: "What should we call you?" with language choice.
4. The hub (or the `return_to` module).

"Use a password instead" is a quiet secondary link on step 1. Errors never say
whether an account exists.

## UX03 — Module hub

The hub answers: which ForKhatri capability do I want now? Module portals show
name, tagline and availability; modules the member used recently come first
with a "continue" affordance. An intent bar accepts a plain request and shows
the understood module before opening it. In-development and planned modules are
informative, not misleadingly interactive.

## UX04 — Navigation (revised 2026-09-14)

No tab bar or bottom navigation. A floating command orb gives navigation and
actions. The header keeps the notifications bell immediately left of the
avatar, and the avatar right-most. Every module surface offers a way back to
the hub.

## UX05 — Member context and notifications

The avatar opens an account sheet (name, language, masked phone/email, sign-out). It explains that profile details are managed inside each module.
Settings live in the sheet and do not take space on the hub. A notification
entry point explains its source module without implying a separate identity.

## UX06 — Resilience

If the identity service is unreachable, the hub shows cached portals dimmed and a
clear "ForKhatri is reconnecting" state; sign-in shows a retry state rather than
an error page. Unavailable modules and empty states use the same visual language.
The shell never implies that a module needs its own sign-in.

## Core flow

```text
Open ForKhatri (optionally ?return_to=<module URL>)
  → GET /v1/session
     ├─ 401 → identifier → code → (new) name → signed in
     └─ 200 ─────────────────────────────────────────┐
                                                     ▼
                         safe return_to? ── yes → module (full navigation)
                               │ no
                               ▼
                             Hub → enter module → POST /enter → module
                               ├→ Bell → notifications
                               └→ Avatar → account sheet → sign-out → entry
Module with no/expired session → entrance ?return_to=<module URL>
```
