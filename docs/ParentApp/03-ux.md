# Parent Application UX

## UX01 — Shared entry and session state

The first view establishes ForKhatri as the product. A returning member sees the parent home surface directly. A signed-out member sees the shared ForKhatri entry action. Module names appear after the parent context is established.

## UX02 — Parent home

The home surface answers three questions quickly:

- What can I do now?
- What is new or relevant?
- Which ForKhatri capability should I open?

The page uses a calm summary, clear module cards, quick actions, and a small activity preview rather than a dense feed.

## UX03 — Module discovery

Modules are presented as parts of one ecosystem. Each card communicates purpose, current availability, and what happens when the member selects it. Planned modules are informative, not misleadingly interactive.

## UX04 — Shared navigation

The shell keeps Home, Modules, Activity, and Account available. On smaller screens it becomes a compact bottom navigation. On larger screens it uses a sidebar/header combination. The active context is visible.

## UX05 — Member context and notifications

The member can open account controls and notifications from the parent shell. A notification preview explains its source module without moving the member into a separate app identity.

## UX06 — Resilience

Unavailable data, unavailable modules, and empty activity use the same visual language. The shell remains usable and never implies that the member must sign in again.

## Core flow

```text
Open ForKhatri → shared session check → Parent Home
                                      ├→ Modules → module context
                                      ├→ Activity → shared activity view
                                      ├→ Notifications → source-aware preview
                                      └→ Account → parent settings/profile
```
