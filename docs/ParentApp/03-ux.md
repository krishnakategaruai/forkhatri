# Parent Application UX

## Revision history

| Date | Change | Reason |
|---|---|---|
| 2026-09-13 | Initial UX01–UX06 and core flow for the static shell. | First reviewable parent slice. |

## UX01 — Shared entry and session state

The first view establishes ForKhatri as the product. A member with a valid
session goes straight to the hub, or straight to the module named in a safe
`return_to`. A signed-out member sees one conversational card. When arriving
from a module, the card names it ("Sign in to continue to Milavn").

## UX02 — Conversational sign-in

One question at a time, each step replacing the last with a transition:

1. "Your phone number or email" — a 10-digit Indian mobile is accepted without `+91`.
2. "Enter the 6-digit code sent to +91•••••43210" — auto-submits on the sixth digit; resend becomes available when the countdown ends; a wrong code keeps the member on the step with remaining attempts implied, and an expired or exhausted code offers a fresh one.
3. New members only: "What should we call you?" with language choice.
4. The hub (or the `return_to` module).

"Use a password instead" is a quiet secondary link on step 1. Errors never say
whether an account exists.

## UX03 — Module hub

The hub answers: which ForKhatri capability do I want now? Module portals show
name, tagline and availability; modules the member used recently come first
with a "continue" affordance. An intent bar accepts a plain request and shows
the understood module before opening it. In-development and planned modules are
informative, not misleadingly interactive.

## UX04 — Navigation (revised 2026-09-14)

No tab bar or bottom navigation. A floating command orb gives navigation and
actions. The header keeps the notifications bell immediately left of the
avatar, and the avatar right-most. Every module surface offers a way back to
the hub.

## UX05 — Member context and notifications

The avatar opens an account sheet (name, language, masked phone/email, sign-out). It explains that profile details are managed inside each module.
Settings live in the sheet and do not take space on the hub. A notification
entry point explains its source module without implying a separate identity.

## UX06 — Resilience

If the identity service is unreachable, the hub shows cached portals dimmed and a
clear "ForKhatri is reconnecting" state; sign-in shows a retry state rather than
an error page. Unavailable modules and empty states use the same visual language.
The shell never implies that a module needs its own sign-in.

## Core flow

```text
Open ForKhatri (optionally ?return_to=<module URL>)
  → GET /v1/session
     ├─ 401 → identifier → code → (new) name → signed in
     └─ 200 ─────────────────────────────────────────┐
                                                     ▼
                         safe return_to? ── yes → module (full navigation)
                               │ no
                               ▼
                             Hub → enter module → POST /enter → module
                               ├→ Bell → notifications
                               └→ Avatar → account sheet → sign-out → entry
Module with no/expired session → entrance ?return_to=<module URL>
```

## SCR-01 Splash
Purpose: brand cover while the session check runs. Elements: wordmark, ambient background. States: shown during `boot`, removed when ready. Out: SCR-02 or SCR-06. Motion removed under reduced motion.

## SCR-02 Arrival, identifier step (verified live)
Heading (h1) "Let's begin. What's your mobile number or email?"; textbox "Mobile number or email" with hint "Enter a 10-digit Indian mobile number or an email address."; button "Send code" (disabled until the input is valid); quiet button "Use a password instead"; line "Your number is never shown to other members."; tagline "Your community. Your opportunities. Your support. Your growth."; five language buttons (current one pressed); dev-only "Development: act as…". A polite live region announces "Step changed: ..."; errors go to an assertive region and never reveal whether an account exists. Return-to kicker: when `?return_to` resolves to a module the card says "Sign in to continue to {module}". Out: SCR-03 (after `POST /v1/auth/code` returns 202), SCR-05, SCR-21.

## SCR-03 Arrival, code step
Identifier collapses into a chip (`.thread-chip`); 6-digit input (`inputmode=numeric`, `autocomplete=one-time-code`) that auto-submits on the sixth digit; resend disabled with a countdown (`.resend-wait`) until `resend_in`; in development a code hint shows. States: busy; wrong code ("isn't right" with shake); expired; attempts exhausted (offers a new code); rate limited (429 with Retry-After text). Out: SCR-06 (existing member) or SCR-04 (outcome `name_required`).

## SCR-04 Welcome step
"What should we call you?" with name field and language choice; `POST /v1/auth/welcome` creates the member (identity level 1). Out: SCR-06 with a welcome greeting.

## SCR-05 Password step
Identifier then password with show/hide toggle. Wrong credentials give one generic invalid-credentials message. For members that have a password (QA and imported members).

## Return-to handling (from `lib/return-to.ts`)
`return_to` is followed only when its origin equals the entrance origin or the origin of a registry `entry_url`, and only for http/https; otherwise ignored. It is removed from the address bar after use. Loop guard: the same target within 20 s (sessionStorage `fk.returnTo.bounce`) keeps the member on the hub. Cross-origin entry carries `fk_handoff`.

## Account deletion (added 2026-11-22)

Built, not screenshot-verified (type-checked only). Component `platform/forkhatri-web/components/DeleteAccount.tsx`, wired into the account sheet (SCR-08, entry "Delete my ForKhatri account") and the entrance. Flow: the sheet shows what is deleted, what is kept and why, asks for the password or a one-time code, asks the member to type DELETE, red button, then per-module progress and a final receipt page, then "Return to ForKhatri" shows the entrance. The sheet cannot be dismissed once deletion has started. If a module is slow the member sees "Your account is closed. Deletion of the rest is finishing." Admin: the Modules page (SCR-17) has a stuck-deletions list with Retry. Module-level delete controls are in each module's `03-ux.md`.
